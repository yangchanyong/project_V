# 9단계 협업 로그: AWS → ARK Migration

## 컨텍스트

8단계에서 AWS(EC2 + Aurora Serverless v2 + S3)에 실제로 배포·운영했던 Project V를, 자체 운영 환경인 ARK로 옮겼습니다. 2026-09-20에 운영 E2E까지 마치고 Migration을 종료했습니다.

이 Migration은 "AWS 리소스를 그대로 옮기는 작업"이 아니었습니다. 기존 AWS 리소스와 데이터는 복구하지 않고, GitHub Source를 기준으로 ARK에 다시 배포하는 방식을 택했습니다. 옮길 운영 데이터가 없었기 때문에 가능한 선택이었습니다.

**전체 흐름**:

```
AWS 복구 포기
  → PostgreSQL 전환 (코드 + vendor-specific Flyway migration)
  → ARK PostgreSQL 연결 (Project V 전용 DB/Role)
  → S3-Compatible Object Storage 전환 (endpoint 분리)
  → Presigned PUT 보안 보강
  → GitHub / GitLab 역할 분리
  → GitLab CI/CD (Runner + Registry + Deploy)
  → ARK Runtime 배포
  → Public HTTPS
  → OAuth / S3 운영 E2E
  → Legacy 정리
```

**최종 운영 상태 (2026-09-20)**:

| 영역 | 현재 상태 |
|------|-----------|
| Source | GitHub `yangchanyong/project_V`가 Canonical (Source of Truth) |
| Delivery | ARK GitLab `ark/project-v`는 CI/CD · Registry · Deploy용 delivery copy |
| DB | ARK PostgreSQL 17, Project V 전용 DB/Role |
| Runtime | 컨테이너 `ark-project-v`, Docker network `ark-internal`, host port 직접 publish 없음, `/actuator/health` UP |
| Public | `https://vibe.chanyongyang.com` — Cloudflare → Nginx → `ark-internal` → `ark-project-v:8080`, Let's Encrypt + Nginx TLS |
| Storage | ARK MinIO AIStor (S3-Compatible), Public Presign endpoint `https://storage.chanyongyang.com`, bucket `project-v` |
| 인증 | Google / Kakao / Naver 운영 로그인 성공 |

**보존한 것**: 8단계의 AWS 운영 경험(`09-aws-ec2-deploy.md`)은 그대로 둡니다. 이 프로젝트는 "AWS에서 실제로 운영해 본 경험"과 "그것을 자체 환경으로 Migration한 경험"을 둘 다 자산으로 가져갑니다.

## AI 제안 vs 최종 결정

### AWS 복구 vs ARK 재배포

- **선택지**: AWS 계정/리소스를 복구해서 그대로 이어가기 vs GitHub Source 기준으로 ARK에 재배포하기
- **최종 채택**: ARK 재배포
- **이유**: 복구해야 할 운영 데이터가 없었습니다. 데이터가 없다면 복구는 비용만 남고 얻는 것이 없고, 재배포는 "Source만 있으면 환경을 다시 만들 수 있다"는 것을 검증하는 기회가 됩니다.
- **Trade-off**: 기존 AWS 운영 상태(데이터, 설정)는 재현하지 않습니다. 이 결정은 "운영 데이터가 필요 없는 포트폴리오 프로젝트"라는 전제에서만 성립합니다. 실사용 데이터가 있는 서비스라면 같은 결정을 할 수 없습니다.

### DB: Aurora MySQL 유지가 아니라 PostgreSQL 17 전환

- **최종 채택**: PostgreSQL 17로 전환
- **MySQL migration을 지우지 않고 vendor-specific으로 보존**: `db/migration/mysql/`(원본 그대로, 체크섬 무변경)과 `db/migration/postgresql/`(신규)를 나눴습니다. 기존 파일을 덮어쓰면 Flyway 체크섬이 깨지고, 무엇보다 "MySQL로 운영했던 이력"이 사라집니다.
- **AI가 실제로 잡아낸 호환성 이슈**: `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY`, `DATETIME(6)` → `TIMESTAMP(6)`, `TINYINT(1)` → `BOOLEAN`, `NOW(6)` → `NOW()`, `LAST_INSERT_ID()` → `INSERT ... RETURNING id`
- **Entity의 `columnDefinition = "DATETIME(6)"`도 제거**: 스키마 변경은 마이그레이션 파일로만 한다는 원칙과 별개로, Entity에 MySQL 전용 타입 문자열이 박혀 있으면 DB를 바꿀 수 없습니다. Hibernate 기본 timestamp 매핑에 맡겼습니다.
- **당시 검증**: PostgreSQL 전환 직후 전체 테스트 52개 통과 (이후 Presigned 보강 등으로 테스트가 늘어 66개)

### Object Storage: S3 API를 새로 만들지 않고 S3-Compatible Storage 채택

- **최종 채택**: ARK MinIO AIStor(S3-Compatible) + 기존 AWS SDK v2 + `StorageService` 구조 재사용
- **이유**: 애플리케이션 코드가 S3 프로토콜에 의존하지 특정 벤더에 의존하지 않도록 이미 `StorageService`로 분리해 두었기 때문에, endpoint와 credential만 바꾸면 되는 구조였습니다.
- **Internal endpoint와 Public Presign endpoint 분리**:
  - `S3Client`(HeadObject/DeleteObject 등 서버 내부 통신)는 `aws.s3.endpoint` = `http://ark-object-storage:9000`
  - `S3Presigner`(클라이언트에게 내려주는 URL)는 `aws.s3.presign-endpoint` = `https://storage.chanyongyang.com`
  - 하나로 합치면 Presigned URL에 Docker 내부 hostname이 노출됩니다. 서명은 host를 포함하므로 나중에 호스트만 바꿔서 해결할 수도 없습니다. 그래서 처음부터 두 endpoint를 분리했습니다.
- **path-style 강제**: MinIO 등 S3-Compatible 백엔드는 virtual-hosted-style을 기본 지원하지 않는 경우가 많아 `path-style-access=true`
- **환경변수 이름 정리**: `AWS_*` 대신 역할 중심의 `S3_*`로 변경 (`S3_BUCKET`, `S3_ENDPOINT`, `S3_PRESIGN_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`)
- **서비스 전용 credential**: Root/Admin credential은 애플리케이션에 쓰지 않고, Project V 전용 IAM credential을 발급해서 사용
- **Bucket CORS**: Origin을 `https://vibe.chanyongyang.com`으로만 제한

### Public Storage hostname: `storage.vibe...` → `storage.chanyongyang.com`

- **초기 후보**: `storage.vibe.chanyongyang.com` (앱 도메인의 하위로 묶는 것이 자연스러워 보였음)
- **문제**: Cloudflare Universal SSL이 기본 제공하는 와일드카드 인증서 범위는 1단계 서브도메인(`*.chanyongyang.com`)까지라, 2단계 nested subdomain은 그 범위 밖입니다.
- **최종 결정**: 1단계 서브도메인 `storage.chanyongyang.com`을 canonical hostname으로 전환
- **정리**: 초기 후보 `storage.vibe.chanyongyang.com`은 2026-09-20에 Nginx HTTP/HTTPS block, Let's Encrypt certificate, Cloudflare DNS record를 모두 삭제했고, Nginx 참조 없음과 DNS 미해석을 확인했습니다. 지금은 hostname 하나(`storage.chanyongyang.com`)만 씁니다.

### GitHub / GitLab 역할 분리

- **문제**: ARK CI/CD는 ARK GitLab에서 돌지만, 포트폴리오로 공개되는 Source는 GitHub에 있습니다. 양쪽을 다 Source처럼 다루면 어느 쪽이 진짜인지 모호해지고 Source가 중복됩니다.
- **최종 결정**:
  - GitHub `yangchanyong/project_V` = Canonical / Public Source of Truth
  - ARK GitLab `ark/project-v` = CI/CD, Container Registry, Deploy를 위한 delivery copy
  - 로컬 remote: `origin` = GitHub, `ark` = ARK GitLab
- **정리한 것**: GitHub의 AWS OIDC + EC2 SSH 배포용 Legacy CD workflow(`.github/workflows/cd.yml`)는 제거하고 새 GitHub Deploy workflow로 대체하지 않았습니다. GitHub `ci.yml`(Public CI)은 유지합니다. GitHub와 GitLab이 동시에 ARK를 배포하는 구조를 만들지 않기 위해서입니다.
- **배포 흐름**:

```
GitHub main (Canonical)
        ↓
GitLab ark/project-v (Delivery Copy)
        ↓
GitLab Runner (test / build)
        ↓
GitLab Registry (commit SHA image)
        ↓
ARK Deploy (docker compose)
        ↓
Health Check (/actuator/health)
```

- **CI 테스트 DB 전략**: ARK 일반 Runner는 Docker socket이 없고 privileged가 아닙니다. Runner에 socket을 붙이지 않고, 공통 template이 제공하는 `postgres:17` service를 datasource로 쓰도록 했습니다. 테스트 코드는 `SPRING_DATASOURCE_URL` 환경변수가 있으면 그대로 쓰고(GitLab CI), 없으면 Testcontainers PostgreSQL을 띄웁니다(Local, GitHub Actions). 테스트를 skip하거나 Runner 권한을 올리는 방법은 쓰지 않았습니다.
- **Docker JAR 결정성**: `./gradlew build`는 executable bootJar와 `*-plain.jar`를 둘 다 만들 수 있어서, `COPY build/libs/*.jar`가 어느 것을 잡을지 환경에 따라 달라질 수 있었습니다. plain jar 생성을 끄고(`tasks.named('jar') { enabled = false }`) artifact가 항상 하나가 되도록 했습니다.

### Presigned 보안

- **`Content-Length-Range` vs exact `Content-Length`**: 이 둘은 다른 기능입니다. 범위 조건(`content-length-range`)은 POST Policy 전용이고 PUT Presigned URL에는 쓸 수 없습니다. 하지만 정확한 단일 값은 `PutObjectRequest.contentLength()`로 SigV4 `X-Amz-SignedHeaders`에 포함시킬 수 있습니다. 서버가 10MiB 이하로 검증한 `fileSize`를 그대로 서명에 묶으면, 업로드 가능한 유일한 크기가 "검증을 통과한 그 값"이 됩니다.
- **`If-None-Match: *`**: 같은 URL/같은 Key로 재업로드해 이미 저장된 객체를 덮어쓰는 것을 막습니다.
- **HeadObject actual size 검증**: `saveImage()`에서 HeadObject 한 번으로 존재 여부와 실제 `contentLength`를 함께 받아 10MiB를 다시 검증합니다. HeadObject를 두 번 부르지 않도록 `OptionalLong findObjectSize(String)`로 계약을 바꿨습니다.
- **UUID 서버 생성 Key, contentType 허용 목록**은 5단계부터 유지
- **실제 AIStor 운영 E2E까지 확인** (아래 표)

**AIStor 운영 E2E 결과 (2026-09-20)**:

| 시나리오 | 결과 |
|----------|------|
| 정상 Presigned PUT (exact Content-Length) | HTTP 200 |
| Content-Length 불일치 | non-2xx로 차단 |
| `If-None-Match: *`가 서명된 동일 Key 재업로드 | HTTP 412 |
| HeadObject 실측 size 검증 + metadata 저장 | HTTP 201 |
| Presigned GET | HTTP 200, 다운로드 body가 원본과 일치 |
| 허용 CORS Origin | 정상 |
| 비허용 Origin | 차단 |
| 10MiB + 1 byte 업로드 | HTTP 413 |

## AI가 놓친 부분

이 항목들은 비난이 아니라 "AI 협업에서 어떤 검증 게이트가 필요한가"를 남기기 위한 기록입니다.

### 1. Content-Length를 서명할 수 없다고 과하게 일반화

5단계에서 AI와 함께 "PUT Presigned URL은 `Content-Length-Range`를 서명할 수 없다"고 결론 내렸는데, 이것이 어느새 "Content-Length 자체도 서명할 수 없다"에 가까운 판단으로 굳어졌습니다. 범위 조건이 안 된다는 사실은 맞았지만, 정확한 단일 값 서명 가능성은 확인하지 않은 채 넘어갔습니다.

Presigned 보안을 다시 다루면서 JShell로 AWS SDK v2 2.29.52의 실제 presign 결과(`signedHeaders()`, `X-Amz-SignedHeaders`)를 직접 뽑아 확인했고, exact Content-Length와 `If-None-Match`가 모두 서명 대상이라는 것을 실측한 뒤에야 보강했습니다.

**게이트**: "불가능하다"는 결론은 무엇이 불가능한지(범위 조건인지, 값 자체인지)를 쪼개서 기록하고, 가능하면 실측으로 확인한 뒤에 확정합니다.

### 2. Public TTFB 약 19.7초 — 내부 상태가 정상이어도 Public이 정상은 아니었다

ARK 배포 후 `vibe.chanyongyang.com` Public 요청의 TTFB가 약 19.7초까지 나왔습니다. 그런데 Origin Nginx를 직접 호출한 응답과 Nginx → Project V 구간은 수십 ms 수준으로 정상이었습니다. 애플리케이션과 Nginx 내부만 보면 문제가 없어 보이는 상태였습니다.

계층별로 latency를 나눠 재면서 "Application / Nginx는 정상, Public 경로에만 지연이 있다"까지 좁혔고, 최종적으로 Cloudflare DNS에 과거 AWS A record가 ARK record와 함께 남아 있는 것을 사람이 확인했습니다. 구 AWS record를 삭제하자 Public 응답이 정상화되었습니다.

**여기까지만 기록합니다**: 구 AWS DNS record의 중복 잔존이 실제 원인이었고, 삭제 후 정상화되었다. 지연이 발생한 Cloudflare 내부 메커니즘(retry/fallback 등)은 증명하지 못했으므로 추측해서 적지 않습니다.

**게이트**: Migration에서는 새 환경만 확인하지 말고, 옛 환경의 잔존 리소스(DNS 등)도 명시적으로 점검합니다. 원인 격리는 계층별 측정이 결정적이었습니다.

### 3. AI가 준 infra 명령이 Secret을 노출시킬 수 있었다

Migration 중 infra 작업에서 AI가 제안하는 명령이 `.env` 전체 출력, Runner config 전체 출력, credential 원문 확인처럼 Secret이 출력(화면/로그)에 남을 수 있는 형태가 될 가능성이 있었습니다. 이후에는 이런 명령을 피하고, 값 자체가 아니라 존재 여부, 권한, 연결 성공 여부 같은 secret-safe한 방식으로 검증하도록 바꿨습니다. Secret 값은 이 문서를 포함해 어디에도 기록하지 않습니다.

**게이트**: 인프라 명령은 실행 전에 "이 출력에 Secret이 섞일 수 있는가"를 먼저 확인합니다. 검증은 값을 읽는 방식이 아니라 동작을 확인하는 방식으로 설계합니다.

### 4. "구현 완료"와 "운영 E2E 완료"는 다른 검증이었다

Presigned 보강이 `main`에 들어갔을 때 문서에는 "SDK 수준에서는 서명 가능함이 확인됐지만 실제 ARK AIStor가 이 서명된 헤더를 강제하는지는 미확인"이라고 적어 두었습니다. AWS SDK가 무엇을 서명하는가와 스토리지 서버가 그 서명을 실제로 검증하는가는 서로 다른 문제이기 때문입니다.

실제 ARK AIStor에서 다시 확인해서 exact Content-Length 불일치 차단, `If-None-Match` 재업로드 412, HeadObject 검증, GET, CORS, 10MiB+1 byte 413까지 동작을 확인한 뒤에야 "운영 검증 완료"라고 쓸 수 있었습니다. 당시의 "미확인" 기록은 지우지 않고, 이후 검증 결과를 `05-s3-image-upload.md`의 후속 검증 섹션에 시간 순서로 덧붙였습니다.

**게이트**: 문서는 "코드에 들어갔다", "테스트가 통과했다", "실제 환경에서 동작을 확인했다"를 구분해서 씁니다. 실환경에서 확인하지 못한 것은 확인했다고 쓰지 않습니다.

## 학습 포인트

### S3-Compatible Storage가 가능한 이유

S3는 특정 제품이 아니라 HTTP 기반 API 규약입니다. 그래서 AWS SDK가 호출하는 요청(PUT/GET/HEAD/DELETE와 SigV4 서명)을 똑같이 이해하는 서버라면 SDK 코드를 바꾸지 않고 endpoint만 바꿔서 쓸 수 있습니다. PHP에서 DB 드라이버(PDO)만 바꾸면 SQL 서버를 바꿀 수 있는 것과 비슷한 발상입니다. 다만 벤더별로 지원 범위가 조금씩 다르므로(예: path-style, 조건부 쓰기) "호환된다"를 실제 환경에서 검증해야 합니다.

### Presigned URL과 SigV4 SignedHeaders

Presigned URL은 "서버가 미리 서명해 둔 요청"입니다. 서명 대상에 포함된 헤더(`X-Amz-SignedHeaders`)의 값이 실제 요청과 다르면 스토리지가 거부합니다. 그래서 `content-type`, `content-length`, `if-none-match`처럼 서명에 넣은 값이 곧 "클라이언트가 지켜야 하는 계약"이 됩니다. 반대로 서명하지 않은 헤더는 클라이언트가 마음대로 바꿔도 검증되지 않습니다.

### exact Content-Length vs POST Policy의 Content-Length-Range

- POST Policy: 브라우저 form 업로드용. "크기가 0~10MiB 사이"처럼 범위 조건을 정책으로 지정할 수 있음
- PUT Presigned URL: 범위 조건 없음. 대신 정확한 크기 하나를 서명할 수 있음

서버가 먼저 "10MiB 이하"를 검증하고 그 값을 그대로 exact로 서명하면, 결과적으로 상한이 지켜집니다. 브라우저는 `Content-Length`를 JavaScript로 직접 설정할 수 없고(forbidden header) body 크기로 자동 설정하므로, 신고한 크기와 다른 파일을 올리려는 시도가 서명 불일치로 걸러집니다.

### `If-None-Match: *`

"이 Key에 객체가 없을 때만 저장하라"는 조건부 쓰기입니다. 값이 이미 있으면 412를 돌려주므로 잠금 없이도 덮어쓰기를 막는 낙관적(optimistic) 방어가 됩니다. 브라우저는 이 헤더를 자동으로 붙이지 않으므로 클라이언트가 직접 보내야 하고, 그 요구사항은 `docs/api-spec.md`에 문서화했습니다.

### HeadObject의 역할

Presigned PUT은 서버를 거치지 않는 클라이언트 → 스토리지 직접 업로드라서, 서버는 업로드가 정말 됐는지, 크기가 얼마인지 모릅니다. `saveImage()` 시점에 HeadObject로 실측 크기를 확인하는 것이 서버가 가진 유일한 "사후 확인" 수단입니다. 신고값이 아니라 실측값을 믿습니다.

### Reverse Proxy와 Forwarded Header

Cloudflare/Nginx 뒤에서는 Spring이 받는 요청이 HTTP처럼 보이기 때문에, OAuth2 `redirect_uri`가 `http://`로 만들어질 수 있습니다. `server.forward-headers-strategy=framework`로 `X-Forwarded-Proto`를 신뢰하게 해서 해결했고, Migration 후에도 Google/Kakao/Naver redirect_uri가 모두 운영 HTTPS 기준으로 생성되는 것을 확인했습니다.

### 계층별 latency 분리

"느리다"는 하나의 증상이지만 원인은 Cloudflare / Nginx / Application 어디에나 있을 수 있습니다. 각 계층을 따로 재서(Origin 직접, Nginx → App, Public) 어디서부터 느려지는지 좁히는 것이 원인 격리의 핵심이었습니다.

### GitHub Canonical + GitLab Delivery 구조

Source of Truth는 하나만 두고, 나머지는 그 복사본으로 역할을 명확히 나눕니다. 그래야 "어느 쪽 코드가 진짜인가"와 "누가 배포하는가"가 헷갈리지 않습니다.

### Commit SHA 이미지 배포와 Health 검증

이미지 태그를 commit SHA로 하면 "지금 떠 있는 것이 정확히 어느 커밋인가"를 추적할 수 있고, 문제가 생기면 이전 SHA 이미지로 되돌릴 수 있습니다. 배포 직후 `/actuator/health`가 UP인지 확인해서 컨테이너가 떴다는 사실이 아니라 앱이 정상이라는 사실을 확인합니다. DB 연결이 끊기면 health가 DOWN이 되므로 운영 DB 이상을 건강한 것으로 오판하지 않습니다.

### vendor-specific Flyway migration

DB 전환 때 기존 migration 파일을 고치면 체크섬이 깨지고 과거 이력도 사라집니다. 벤더별 디렉터리(`mysql/`, `postgresql/`)로 나누고 설정(`spring.flyway.locations`)으로 선택하면, 과거 이력은 그대로 보존하면서 새 DB에 맞는 스키마를 새로 만들 수 있습니다.

### Migration에서 Historical Experience를 보존하는 방법

새 환경으로 옮겼다고 과거 경험을 새 경험으로 덮어쓰면 "AWS에서 운영해 본 경험"과 "환경을 Migration한 경험" 둘 중 하나가 사라집니다. 문서를 Current(현재 운영 상태)와 Historical(당시 사실, 당시 판단)로 분리해서, 현재를 설명하는 문장만 갱신하고 과거 기록은 시간 순서가 보이게 보존했습니다.
